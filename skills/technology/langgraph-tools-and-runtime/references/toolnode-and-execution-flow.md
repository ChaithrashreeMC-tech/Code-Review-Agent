# ToolNode & Execution Flow

This reference documents `ToolNode` mechanics, tool-call routing, `ToolMessage` association by ID, parallel tool execution, and execution flow patterns in LangGraph.

---

## 1. ToolNode Responsibilities & Execution Mechanics

`ToolNode` (from `langgraph.prebuilt import ToolNode`) executes tool calls extracted from the latest message in the state:

1. **Inspects Last Message**: Reads the latest `AIMessage` in `state["messages"]`.
2. **Extracts Tool Calls**: Loops over `message.tool_calls`, where each call is a dict `{"name": str, "args": dict, "id": str}`.
3. **Executes Tools**: Finds the matching tool by `name` and executes it with `args`.
4. **Produces ToolMessages**: Generates a `ToolMessage(content=..., tool_call_id=call["id"])` for each executed call.
5. **Appends to State**: Returns `{"messages": [ToolMessage, ...]}` which are appended to the state via the `add_messages` reducer.

---

## 2. Tool Call & Tool Message ID Association

LangGraph and LLM providers strictly require every `ToolMessage` to match the `tool_call_id` generated by the model.

```text
User: "Check weather in NY and London"
  |
  v
LLM Node -> AIMessage(tool_calls=[
              {"name": "get_weather", "args": {"city": "NY"}, "id": "call_1"},
              {"name": "get_weather", "args": {"city": "London"}, "id": "call_2"}
            ])
  |
  v
ToolNode -> Returns messages: [
              ToolMessage(content="Sunny, 22C", tool_call_id="call_1"),
              ToolMessage(content="Rainy, 15C", tool_call_id="call_2")
            ]
  |
  v
LLM Node -> Receives ToolMessages, synthesizes final response to User.
```

> **Critical Defect Pattern: Unassociated Tool Call IDs**
> If a custom tool runner returns a `ToolMessage` without a `tool_call_id` or with a mismatched ID, the model provider API (OpenAI, Anthropic) will reject the subsequent invocation with a 400 Bad Request error.

---

## 3. Parallel Tool Execution

Modern chat models often emit multiple tool calls in a single turn (e.g. `call_1` and `call_2` simultaneously).
- `ToolNode` handles multiple tool calls within a single invocation.
- If individual tools perform async I/O, `ToolNode` or async graph runners execute them concurrently where supported.
- If one tool fails in a multi-call batch, `ToolNode` catches the error and generates an error `ToolMessage` for that specific call ID, allowing the other calls to succeed and return normally.

---

## 4. Graph Routing: Conditional Edges vs Deterministic Nodes

### A. Dynamic Model-Tool Loop (ReAct Pattern)
Use `tools_condition` or custom routing to decide whether to execute tools or finish:

```python
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode, tools_condition

builder = StateGraph(AgentState)
builder.add_node("agent", call_model_node)
builder.add_node("tools", ToolNode(tools))

builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition, {"tools": "tools", END: END})
builder.add_edge("tools", "agent")
```

### B. Deterministic Workflows (No ToolNode Required)
When a workflow follows a fixed deterministic pipeline (e.g. Extract -> Validate -> Transform -> Save), invoke application services directly within standard graph nodes:

```python
async def validate_document_node(state: WorkflowState) -> dict:
    # Direct service call without LLM tool-calling overhead
    result = await document_service.validate(state["doc_id"])
    return {"is_valid": result.is_valid, "errors": result.errors}
```

> **False-Positive Safeguard:** Do NOT require `ToolNode` or `bind_tools` when the workflow is intentionally structured as deterministic nodes invoking application services.
